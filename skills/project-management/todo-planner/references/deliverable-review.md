# Discovery Deliverable Review

Use this reference to review completed or in-review discovery work, including
Process Mapping, Meeting / Discussion, SPIKE, Documentation, and Process
Assessment todos. The goal is a fair verdict based on the actual output and
evidence, not just its Basecamp state.

## Evidence first

Read the todo description, comments, linked artifacts, and relevant
attachments. Compare each Acceptance Criterion / Done Criterion with the
evidence. A checked subtask, completed todo, or statement by the assignee is
not proof by itself.

Keep these separate:

- **Quality verdict:** whether the criteria are fulfilled.
- **Recorded state:** the current Basecamp state, if known.

A verbal decision or validation can satisfy a criterion unless written approval
is explicitly required. In that case, record the person, decision, and date in
the review, and recommend a short Basecamp note for traceability.

## Discovery is not solution design

Discovery work should document the current process accurately and make the
supporting evidence easy to review.

- Keep improvement ideas in a separate backlog or follow-up section.
- Do not allow improvement ideas to stand in for an incomplete current-state
  map.
- Mark claims as **observed**, **confirmed by [person]**, or **open question**.
  Do not turn assumptions into facts.

For a process map, look for the trigger, agreed start and end boundary, roles,
systems/artifacts, handoffs, main flow, and open questions. When the material
is too detailed for a readable Basecamp comment, use a reviewable artifact such
as a Google Sheet or diagram.

## Content and clarity checks

Apply only the checks that fit the requested deliverable:

- **Coverage:** Each named sheet, system, branch, or artifact has enough detail.
  A complete map of one sheet does not prove a second named sheet was mapped.
- **Inputs:** State the exact source, field or artifact, owner, transfer method
  (manual, copy-paste, upload, automatic), and trigger. “From source” is not
  enough.
- **Outputs:** State the resulting artifact, next user or recipient, and link a
  sample or supporting evidence where possible.
- **Field map:** Include each field's meaning, owner, exact source, input method,
  update trigger, and downstream use.
- **Terms:** Define acronyms, labels, and categories such as VOS A/B if a new
  reviewer would not know their meaning, role, or owner.
- **Evidence:** Link screenshots, sample records, source documents, or interview
  notes to material claims. A screenshot should show the relevant step, not only
  the name of a tool.
- **Format:** Prefer a concise overview plus field map, evidence links, and
  glossary/open questions. Request a clearer format only when it will materially
  improve reviewability.

## Response shape

Use one unambiguous verdict:

- **Complete:** All criteria have adequate evidence.
- **Complete, record validation:** Criteria are met based on verbal or external
  confirmation, but Basecamp should record it.
- **Needs Revision:** One or more criteria lack enough content or evidence.
- **Not ready to assess:** The needed artifact or evidence is unavailable.

Then return:

1. **Acceptance Criteria:** Met, Partial, Not Met, or Not Verifiable, with
   concise evidence.
2. **Required revision:** the smallest changes needed to reach Complete.
3. **Optional follow-ups:** useful ideas that are outside the current discovery
   scope.

Write feedback in the user's language. State observable gaps; do not judge the
author or speculate that the material was AI-generated.
